My home server

Two boxes, one NixOS flake, media and photos for the household. Written for you to poke holes in.

The hardware

NASSynology DS420+ (Celeron J4025, 6 GB), four disks in SHR-1 with btrfs, 5.3 TiB usable, data checksums on. It does one job: store bytes and serve them over NFS. It runs no containers at all.
ServerAn old ThinkBook 16p (Ryzen 9 5900HX, RTX 3060 with 6 GB, 32 GB RAM, 1 TB NVMe), lid closed on a shelf, on NixOS 26.05. It runs everything else. Wired through a USB-C ethernet dongle with Wi-Fi as a standing failover, which I tested by pulling the dongle.

I first planned to keep the media stack on the NAS. Then I checked: the Celeron can't tone-map 4K HDR in real time, so every client except the Shield would have got a broken stream. That's why the compute moved to the laptop and the NAS went back to being plain storage.

What runs

  • Jellyfin with NVENC and CUDA tone mapping on the 3060. The Shield direct-plays 4K HEVC HDR. Phones and browsers get a GPU transcode, which I checked in the ffmpeg log (hevc_nvenc plus tonemap_cuda).
  • Jellyseerr for requests, Radarr and Sonarr for films and shows, Prowlarr for the indexer, SABnzbd for downloads. Usenet via Eweka and NZBgeek.
  • All of it is plain podman containers declared in the flake, with pinned image versions. No docker-compose files scattered around.
  • Coming next: Immich on the same GPU, then restic backups and alerting (details at the end).
request (Jellyseerr) -> Radarr / Sonarr -> Prowlarr -> NZBgeek -> SABnzbd (downloads from Eweka, unpacks on local NVMe) -> import into /data/media -> Jellyfin

SABnzbd unpacks on the NVMe on purpose: par2 and unrar are heavy random I/O, and I didn't want that on the array. The finished file crosses the LAN once. Because usenet/complete and media sit in one NFS export, the import is a rename on the NAS, not a copy. I tested it: a 200 MB move took 5 ms and kept its inode.

Storage and the NFS mount

One mount carries the media and the photos, so I treated it as a hard dependency instead of hoping it stays up:

  • NFSv4.1 with hard (never soft) and x-systemd.automount. Every service orders itself on its mounts with RequiresMountsFor.
  • The same paths (/data, /photos) inside every container, which is what keeps imports cheap.
  • A small mount-guard script that the backup job has to call first. The failure I most wanted to design out: restic snapshots an unmounted, empty directory, writes a near-empty snapshot, and the next forget --prune ages out the real history. The guard checks for a live NFS mount from the NAS, and I tested it against a stopped mount, a local directory and a missing path.

Security

  • Nothing is exposed to the internet. I don't forward any ports on the router. QuickConnect is off on the NAS. Remote access is Tailscale only, with key expiry off on both nodes so they don't drop off the tailnet.
  • SSH is key-only on the server, root included. Root can log in only with my key, because that's how I deploy from my desktop with nixos-rebuild --target-host. No checkout lives on the server.
  • Default-deny firewall on the server. It lets in only SSH and the six web UI ports, which are LAN and tailnet only. I checked from another machine: rpcbind and LLMNR are listening but closed from outside.
  • Secrets are sops-nix. The repo is public, so only ciphertext is in it. The server decrypts with its own SSH host key into /run/secrets (ramfs), never onto disk and never into the Nix store. Usenet logins, the Wi-Fi password and the Tailscale key all go through it. The only thing to back up is my personal age key, which lives in a password manager and on paper.
  • NFS exports are restricted to the server's two addresses (wired and Wi-Fi), which I bound by MAC on the router. The NAS's own admin account is disabled and DSM SSH is on a non-default port with key auth.
  • Every web UI has a login. The arrs and SABnzbd were open until I set that up on day one.

Trade-offs I made knowingly. Exports use "map all users to admin", so every write lands as one UID. That makes container permissions trivial, but there is no per-service ownership on the NAS. Web traffic on the LAN is plain HTTP; off the LAN it's inside Tailscale. Jellyfin and Jellyseerr containers run as root, while the arrs and SABnzbd run as the NAS user.

Keeping the data safe

  • Rebuilding the NAS. I wiped and rebuilt it as a clean SHR-1 instead of expanding it live, since an online reshape on a Celeron, with the family photos as the only copy, was the riskiest step in the plan. Before the wipe, a SHA-256 manifest hashed on the NAS had to match two separate copies, a USB disk and my desktop's NVMe, plus a freeze and a final delta so phone uploads weren't lost.
  • The photos share has daily btrfs snapshots. Scrub runs every two months, SMART quick weekly and extended every three months, staggered so they never share a day.
  • Media is deliberately not backed up. It's re-downloadable, and the array is a rotating pool: when it fills I delete first.

The config itself

Both machines and my desktop are one flake. Servers roll back like any NixOS box, CI runs nix flake check on every push, and the whole thing is documented in tickets with checklists, so I can always tell what was verified and what wasn't. The apps' own settings (indexer, quality profile, root folders) live in each app's config under /var/lib, not in Nix. That's the one place it isn't declarative, and it is in the backup scope.

Still open, so you don't have to find it

  • No UPS on the NAS. The photos export is sync and the media export async for that reason, so a photo write is acknowledged only once it is on disk.
  • No offsite copy yet. I wanted Google Drive, but my Google account situation is unsettled, so I deferred it. Until then the 3-2-1 isn't complete.
  • Backups (restic, 3-2-1), Immich and alerting are next. Alerting will be dead-man style, healthchecks pings from every timer, so a job that fails for months looks different from a job that works.
  • The NAS RAM test must pass before I import the photo library, and the first array resync should finish. Idle power and thermals on the laptop are still unmeasured.
